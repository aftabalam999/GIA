## 1. Executive Summary & Critical Issue Analysis

### 1.1 The Critical Provenance Vulnerability
In previous iterations, the authorization pipeline accepted an `isAssistantVoice: boolean` flag submitted by the client in the `/approve` HTTP payload. This presented a fundamental security risk:
- **Client Untrustworthiness**: Any HTTP client, malicious local script, or attacker with network access could submit `isAssistantVoice: false` (or omit the field), falsely claiming that an audio transcript originated from a human voice.
- **Acoustic Feedback Indistinguishability**: In an acoustic environment where desktop speakers play assistant speech, physical sound waves enter the laptop's microphone. To the analog microphone diaphragm, operating system audio driver, and VAD/Whisper models, acoustic pressure waves generated by the speaker look identical to speech spoken by a human in the room.
- **The Core Invariant**: **A backend cannot cryptographically determine whether an audio transcript originated from a human voice merely because an untrusted client or frontend asserts it as user speech.**

### 1.2 The Hardened Architectural Remedy
Rather than pretending a client-side boolean establishes trusted audio provenance, Phase 5.3 implements **Defense-in-Depth Authorization Hardening**:
1. **Zero Trust in `isAssistantVoice: false`**: The backend never uses client assertions of human origin to make an authorization decision.
2. **Mandatory UI Confirmation for High-Impact Actions**: Any plan containing sensitive operations (permanent deletion, file overwrites, privileged commands, system configuration changes, financial transactions, private credential access) **strictly prohibits voice authorization**. High-impact actions require trusted explicit web UI confirmation with step-specific sensitive confirmations.
3. **Session, Conversation, and Plan Cryptographic Binding**: Voice approvals for low-risk actions are strictly bound to the authenticated user ID, active conversation ID, exact pending plan ID, and exact validated plan version.
4. **Anti-Replay & Freshness Windows**: Voice approvals are single-use (tracked via SHA-256 transcript nonces), require timestamps strictly subsequent to plan presentation, and expire after 60 seconds.
5. **Mandatory Cryptographic Execution Tickets & Argument Integrity**: Action execution requires a signed HMAC `ExecutionTicket`. Tool execution validates that arguments match the approved plan step, detecting and rejecting argument tampering.

### Scenario Test Details:
1. **Forged `isAssistantVoice: false`**: Created a plan containing permanent file deletion (`/etc/gia/config.json`). Submitted a voice command with explicit approval and `isAssistantVoice: false`. Verification confirmed approval was blocked with `"High-impact actions require trusted explicit UI confirmation"`, and plan remained in `pending` status.
2. **Replayed Approval Transcript**: Verified that an initial voice approval succeeds, but submitting an identical transcript/nonce signature returns `"Approval denied: Replayed voice approval detected"`.
3. **Stale Approval**: Verified that a transcript timestamp prior to plan creation (received before confirmation prompt) is rejected, and a timestamp older than 60s is rejected as expired.
4. **Wrong Plan ID**: Verified that approval for non-existent UUID throws `NotFoundError` (404).
5. **Wrong User**: Verified that an attacker attempting to approve a victim's plan throws `AuthorizationError` (403 IDOR prevention).
6. **Modified Execution Arguments**: Approved a step for `{ appName: 'Google Chrome' }`. Attempting execution with `{ appName: 'MaliciousAppExploit' }` was detected by `verifyToolExecution` and denied with `"Execution argument tampering detected"`.
7. **Expired Ticket**: Verified that an execution ticket aged beyond its 10-minute TTL returns `"Execution ticket has expired"`.
8. **Rejected Plan**: Confirmed that once a plan is rejected via `rejectPlan`, subsequent approval attempts fail with `"A rejected plan must never execute"`, and plan execution fails.
9. **Missing Approval**: Verified that tool execution without a ticket token fails with `"Explicit user approval ticket is mandatory"`, and plan execution fails.
10. **Valid Explicit UI Approval**: Confirmed that a sensitive plan with checked step-specific confirmation (`step_1_PERMANENT_DELETION: true`) succeeds through `channel: 'web_ui'`, generating an approved `gia_ticket_<hex>` token that authorizes legitimate execution.

## 5. Architectural Security Documentation & Limitations

### Trusted Audio Provenance Limitation
> [!IMPORTANT]
> The GIA-AI architecture explicitly documents that **audio provenance cannot be established from client-provided speech transcripts alone**. Therefore:
> 1. Speech transcripts are categorized as untrusted input.
> 2. Voice commands may only be used to authorize low-risk, non-destructive actions.
> 3. High-impact and sensitive operations require the user to interact with the trusted graphical interface (`channel: 'web_ui'`), ensuring human intentionality and cryptographic auditability.
